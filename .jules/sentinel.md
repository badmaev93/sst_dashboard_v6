## 2026-07-18 - [Missing Access Controls on Sensitive Personnel and Operational Endpoints]
**Vulnerability:** Critical GET endpoints (`/api/monitoring/users/personnel`, `/api/monitoring/requests/`, and `/api/monitoring/equipment/checks`) were completely public and did not implement FastAPI's dependency-injection-based authentication or role checks. This allowed unauthenticated attackers to exfiltrate database records of all personnel (including PII such as full names, phone numbers, and positions) and internal operational requests/checks.
**Learning:** Handlers were added dynamically over various versions of the API routers, and because there was no router-level prefix security dependency, individual routes were mistakenly left public. Developers assumed that frontend UI filtering (`cabinet.js` only rendering the UI for supervisors) was sufficient security (client-side security theater).
**Prevention:** Always enforce backend-level authentication and authorization checks (`Depends(get_current_user)` or `Depends(require_role(...))`) on every endpoint returning sensitive data. Never rely on frontend UI hiding or client-side checks for access control.

## 2026-07-24 - [Fail-Open Webhook Key Validation and Missing Calendar Update Controls]
**Vulnerability:** First, unconfigured agent webhook keys (`AGENT_API_KEY=""`) allowed attackers to bypass authentication entirely by providing an empty `X-Agent-Key` header (matching `"" == ""`). Second, the calendar event update endpoint (`/api/monitoring/calendar/events/{event_id}` PUT) lacked role-based access checks, allowing any authenticated user (e.g. observer) to alter official operational schedules.
**Learning:** Simple equality checks on API keys are highly vulnerable to unconfigured environment state (e.g., `""` or `None`), leading to fail-open behavior. Additionally, creating endpoints without aligning authorization requirements with other CRUD operations for the same resource creates severe privilege escalation opportunities.
**Prevention:** Implement fail-secure validation (`not SECRET or key != SECRET`) to handle unconfigured states. Align access requirements consistently across all write actions (POST/PUT/DELETE) for any sensitive resources.
