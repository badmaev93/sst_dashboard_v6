## 2026-07-18 - [Missing Access Controls on Sensitive Personnel and Operational Endpoints]
**Vulnerability:** Critical GET endpoints (`/api/monitoring/users/personnel`, `/api/monitoring/requests/`, and `/api/monitoring/equipment/checks`) were completely public and did not implement FastAPI's dependency-injection-based authentication or role checks. This allowed unauthenticated attackers to exfiltrate database records of all personnel (including PII such as full names, phone numbers, and positions) and internal operational requests/checks.
**Learning:** Handlers were added dynamically over various versions of the API routers, and because there was no router-level prefix security dependency, individual routes were mistakenly left public. Developers assumed that frontend UI filtering (`cabinet.js` only rendering the UI for supervisors) was sufficient security (client-side security theater).
**Prevention:** Always enforce backend-level authentication and authorization checks (`Depends(get_current_user)` or `Depends(require_role(...))`) on every endpoint returning sensitive data. Never rely on frontend UI hiding or client-side checks for access control.

## 2026-07-20 - [PII Leakage and Violation of Principle of Least Privilege in Schedule Endpoints]
**Vulnerability:** Standard scheduling and assignment endpoints (such as `GET /api/monitoring/schedule/`, `/personnel`, `/today`, and `/upcoming`) returned the phone numbers of all personnel (`p.phone`) to all logged-in users regardless of their roles (e.g., low-privilege observers). This leaked PII to unauthorized users, as the frontend did not even display phone numbers.
**Learning:** SQL queries were copy-pasted or written with excessive SELECT parameters, pulling in sensitive database columns that were unnecessary for the scheduling view, thereby ignoring the Principle of Least Privilege and Data Minimization.
**Prevention:** Only select and return columns that are strictly necessary for the intended frontend UI view. Implement role-based property filtering or restrict sensitive column retrieval entirely to secure administrative endpoints (e.g., `GET /api/monitoring/users/personnel`).

## 2026-07-21 - [BOLA and Privilege Escalation in Request Modification]
**Vulnerability:** The PUT endpoint for request updating (`/api/monitoring/requests/{req_id}`) was accessible to any logged-in user without checking if the user was the request creator or a supervisor. This allowed BOLA / IDOR manipulation. Furthermore, a non-supervisor could modify the request status directly to administrative states like 'signed' or 'rejected', entirely bypassing the supervisor approval signature flow.
**Learning:** Endpoints allowing mutations (PUT/PATCH/DELETE) require checking ownership/creatorship of resources or role-based access control (RBAC). Simply verifying that a user is authenticated (`get_current_user`) is not sufficient for update or delete requests.
**Prevention:** Always implement rigorous object-level ownership checks and restrict status transitions to allowed roles on any mutation endpoint. Never trust input payloads (like `status`) without checking the current user's role permissions.

## 2026-07-29 - [BOLA and Unauthorized Modification in Calendar Event Updates]
**Vulnerability:** The PUT endpoint for calendar event updates (`/api/monitoring/calendar/events/{event_id}`) was accessible to any logged-in user without any ownership or role validation. A low-privilege observer could edit any calendar event (such as crucial shift schedule changes or maintenance events) created by supervisors or engineers.
**Learning:** This is a recurring Broken Object Level Authorization (BOLA) pattern in this codebase. Developers secured the event creation (`POST`) with role restrictions (`require_role("engineer", "supervisor")`) and event deletion (`DELETE`) with role restrictions (`require_role("supervisor")`), but mistakenly assumed that standard `get_current_user` was secure enough for updates.
**Prevention:** Every resource modification endpoint (PUT/PATCH/DELETE) must explicitly verify ownership (e.g., `created_by == user["id"]`) or authorized administrative role (e.g., `user["role"] == "supervisor"`) before modifying rows in the database. Never assume authenticated access equals authorized access.
